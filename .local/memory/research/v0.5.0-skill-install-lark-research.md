### §A.4 — `devola-init local --mode={core,standard,full}` mode semantics

The function-level matrix from `main()` at `init_project.py:740-751`:

| `--mode=` | `default_no_compile` | `default_with_examples` | Effect |
| --- | --- | --- | --- |
| `core` | `True` | `False` | Lean install — scaffold `.local/` + `.rules/compile-config.yaml` only, no compile, no examples |
| `standard` (or absent) | `False` | `False` (or `None` → `"all" in targets` fallback) | Default — scaffold + compile rules, no example seeds |
| `full` | `False` | `True` | Full demo — scaffold + compile + seed `.local/.agent/active/example-add-dark-mode/` (7 files) + 1 handoff envelope + 1 source-of-truth spec |

`install_local()` itself (at `init_project.py:241-323`) does the following four things in order on every call (idempotent):

1. `scaffold_local(cwd)` → creates `feedbacks/`, `tasks/`, `memory/`, `.agent/{active,handoff,archive}/`, plus `memory/specs/`, plus `index.md`, plus `feedbacks/TRACKER.md`, plus `memory/MEMORY.md` (workspace.py:11-24,121-182). Also runs `_audit_gitignore_coverage` (workspace.py:294-435) and emits a `WARNING` log per matched `.gitignore` rule recommending `!<path>/README.md` whitelist lines.
2. Materialises `.rules/compile-config.yaml` from the `importlib.resources`-packaged template if absent (`init_project.py:290-298`). This is the v9.2.2 I-001 fix that lets wheel-only installs proceed.
3. If `with_examples=True` (i.e. `--mode=full`), invokes `_seed_example_artifacts(cwd)` (`init_project.py:604-672`) which writes 7 budget-checked artifact files + 1 handoff envelope + 1 source-of-truth spec, gated by `Path.exists()` per S-9 append-only.
4. If `compile_rules=True` (i.e. NOT `--no-compile`), runs `RuleCompiler(config_path).compile_all()` and prints `OK   compiled .rules/ → .cursor/rules/repo-governance.mdc + AGENTS.md`. Exceptions are caught and downgraded to `WARN compile failed (non-fatal): <exc>` per the explicit S-5 graceful-degradation contract documented at `init_project.py:265-271`.

**Wheel-portability invariant** (v9.2.2 PV-01 / I-001): only `local` is exempt from the `agent_dir / "SKILL.md"` existence check at `init_project.py:802-816`; the four targets `{cursor, claude, copilot, codex}` enumerated in `AGENT_DIR_REQUIRED_TARGETS` (`init_project.py:704`) print an informative error and `sys.exit(1)` if the source tree is missing — i.e. they are clone-install-only.

### §A.6 — `devola-init doctor` semantics

`devola-init-doctor` is wired via the `[console_scripts]` `devola-init-doctor = devolaflow.cli:doctor_cmd` and lives at `cli.py:137-155`. The implementation:

```
report = check_init_health(Path.cwd())
icons = {True: "✅", False: "❌"}
for f in report.findings:
    print(f"  {icons[f.ok]} {f.path} — {f.detail}")
print()
if report.healthy:
    print("  All canonical paths present. Workspace is healthy.")
else:
    print(f"  {len(report.missing)} missing path(s): {report.missing}")

```

The actual canonical-manifest check delegates to `devolaflow.lifecycle.validate_owned_files.check_init_health(cwd)`. Exit code is the contract — `0` for healthy, `1` for any missing canonical path. This is the analog of what PopolaLoom needs for v0.5.0 (a `popola doctor` or `popola skill check` verb that audits skill-install + daemon + lark-cli all in one shot).

### §A.7 — Version + upgrade story

The pip wheel route is the canonical upgrade path: `pip install --upgrade git+https://github.com/YoRHa-Agents/DevolaFlow.git`. The README "Quick Install" section also documents a curl one-liner: `curl -fsSL https://raw.githubusercontent.com/YoRHa-Agents/DevolaFlow/main/scripts/install.sh | bash -s cursor` (the `INSTALLER` shell variable). The one-liner takes positional arguments `cursor` / `claude` / `copilot` / `all` / `update` and `--global` / `--project`. Per the README "Troubleshooting installs" §, the documented failure modes are (1) corporate mirrors that ship `setuptools < 68.0` (workaround: `pip install --index-url https://pypi.org/simple/`) and (2) the I-001 wheel-vs-clone gap (resolved in v9.2.2 — `local` works on wheel-only, the four IDE targets need a clone install).

`devola-version` (`cli.py:10-14`) exists as a separate console script that prints `DevolaFlow v{__version__}` — useful as a probe in install scripts.

The runtime plugin registry (`devolaflow plugins {list,status,refresh}`) at `cli.py:177-301` is the v9.4.0 PV-04 daily-upgrade surface: `plugins list` enumerates plugins with install state + last_checked, `plugins refresh [--force] [--plugin <id>] [--json]` upgrades stale plugins (default staleness = > 24 h since last check), exit codes `0/1/2` are stable contract (`cli.py:170-174`). PopolaLoom does not need this complexity at v0.5.0 but should be aware of it as the precedent for any future "popola plugins" surface.

### §A.8 — The `workflow-system/agent/` source tree (clone-install-only)

The wheel does NOT bundle `workflow-system/`. Per `init_project.py:683-704`, the wheel exclusion is **intentional**: the agent source tree (containing `SKILL.md`, `references/`, `examples/`, plus the `.cursor/rules/workflow-rules.mdc` template) is too large to ship as wheel data files and changes far more rapidly than the Python core. Operators who want the four IDE targets must therefore either:

1. `git clone https://github.com/YoRHa-Agents/DevolaFlow && pip install -e ./DevolaFlow`, which makes `_find_agent_dir()` resolve to `<clone>/workflow-system/agent/` (the first candidate at `init_project.py:43`), or
2. Run the curl one-liner installer (which wraps the clone + pip-install internally per the README quick-install section).

The error message at `init_project.py:802-816` is the documented breadcrumb that recovers operators who hit the wheel-only failure mode.

This design pattern matters for v0.5.0: PopolaLoom currently has **no equivalent** of the agent source tree — its skill is a single SKILL.md proxy + the python package. v0.5.0 will need to decide whether to invent an equivalent (more flexibility, more install complexity) or stay single-file (simpler, less skill-richness).

### §B.2 — Body conventions

The lark-* skill bodies (per `~/.claude/skills/lark-im/SKILL.md` and similar) follow a 3-section convention:

1. **Overview** (one paragraph, ~ 100 words) describing what the skill does.
2. **Quick reference** (1-3 examples of the canonical CLI invocation, with comments).
3. **Detailed workflows** (numbered procedures with command + expected output for each step).

The DevolaFlow SKILL.md is much longer (29 KB / 29293 bytes per `ls -la` of `/root/.cursor/skills/devola-flow/SKILL.md`) and mixes a "soul rules" charter, FSM state diagrams, hook contracts, and stage workflows into one file.

For v0.5.0 PopolaLoom should aim for the lark-* compactness (~ 5-10 KB) — the daemon/CLI surface does not justify a 30-KB skill, and large skills hurt token-budget compliance.

### §B.3 — Token budget norms

The DevolaFlow SKILL self-reports `token_estimate: 2800`. Empirically `wc -c` returns 29293 chars; assuming `len(text) // 4` (DevolaFlow's own estimator at `init_project.py:569-579`) the budget is ~ 7300 tokens — i.e. the self-reported `2800` understates the actual cost by ~ 2.6× because the estimate excludes the references/examples siblings. A v0.5.0 PopolaLoom skill that targets 2800 tokens should therefore weigh in around **11000 chars / 11 KB of body**.

### §B.4 — Discovery mechanism (filesystem scan)

Both Cursor and Claude Code discover skills by **filesystem scan** of the canonical directories at session boot:

- Claude Code: `~/.claude/skills/<name>/SKILL.md` (per the README install table) + `<repo>/.claude/skills/<name>/SKILL.md` for project-local skills + `~/.claude/CLAUDE.md` / `<repo>/CLAUDE.md` for the legacy single-file shape.
- Cursor: `~/.cursor/skills/<name>/SKILL.md` (per `install_cursor` at `init_project.py:196-202`) + `<repo>/.cursor/skills/<name>/SKILL.md` for project-local skills. Cursor IDE *also* maintains `~/.cursor/skills-cursor/` for its bundled catalogue (the entries `babysit`, `canvas`, ..., observed on this sandbox), but this directory is not an install target for third-party skills.
- Codex: `$CODEX_HOME/skills/<name>/SKILL.md` per `install_codex` at `init_project.py:229-238`.
- Copilot: `.github/copilot-instructions.md` (single file) per `install_copilot` at `init_project.py:220-226`.

There is **no central registry** — discovery is purely filesystem-based. This means v0.5.0 install only has to drop files in the right places; no JSON manifest, no daemon registration, no IDE restart.

### §B.5 — Manual-attach vs auto-discover

The DevolaFlow `description` frontmatter is the auto-discover hook: when an LLM sees the skill in its index, the `description` is what the routing logic matches against the user's intent. The `triggers` array (DevolaFlow-extended) is a more explicit hook the LLM can pattern-match on. There is **no manual-attach** convention in either ecosystem — once a skill is on disk, it is indexed; the user opts in by phrasing their request to match the description / triggers.

For v0.5.0 PopolaLoom this means the skill description must be tight and unambiguous: e.g. "Use when delegating long-running coding tasks to a local agent CLI (Cursor / Claude / Codex / Copilot) that should survive terminal exit and emit progress events / HITL prompts." Keywords like "delegate", "long-running", "background task", "agent CLI", "supervise" should appear so the LLM routes correctly.

### §D.3 — `send_lark_card` production wiring gap

`send_lark_card` lives at `src/popolaloom/hitl/renderers/lark.py:113-205`. Grep across `src/popolaloom/daemon/` finds **zero production call sites** — only `src/popolaloom/hitl/sync.py:335` (which records the *outcome* of a `send_lark_card` invocation, not invokes it) and the test suite. The only pathway from a daemon event to `send_lark_card` is via the HITL `LarkRenderer` registered in `hitl/sync.py`'s renderer registry, which is invoked when an HITL prompt is materialised — i.e. only the HITL trigger taxonomy currently exercises it. Task lifecycle events (`task.completed`, `task.failed`, the missing `task.canceled`) do not.

This is the single biggest v0.4.1 gap and the user's explicit request: "至少能够让Popola Loom在任务有完成或者有确认状态，这种强需要人类交互的情况下，能够主动通知到用户的机器人上。"

### §D.4 — `daemon/main.py` LarkListener wiring gap

`_build_default_popolad` at `src/popolaloom/daemon/main.py:142-173` wires:

1. The unified `build_command` adapter (L155).
2. `TaskPersistence` from `_build_persistence_safely` (L159).
3. `Popolad(events_dir=..., adapter=..., persistence=...)` (L161-165).
4. `PopolaEventBusBridge` subscribing ArkTower's `EventBus` to NDJSON `task.transition` events (L167-172).

It does **not** import `LarkListener` or `LarkSupervisor`, does not check `is_lark_runtime_available()`, does not start a listener subprocess. Inbound Lark cards / chat commands therefore have no ingress unless `popolaloom_lark_listener` (or some other harness) is started out-of-band. v0.4.1 must wire this — either as a positional kwarg into `_build_default_popolad` (preferred — tests can disable it) or as a separate `popola popolad start --with-lark` flag.

### §D.5 — `task.canceled` emission gap

The supervisor at `src/popolaloom/daemon/supervisor.py:220-227` emits exactly two terminal events:

```python
event_type = "task.completed" if exit_code == 0 else "task.failed"
event_log.append(
    event_type,
    {"task_id": task_id, "exit_code": exit_code, "pid": proc.pid},
)
```

The `cancel_task` path at `src/popolaloom/daemon/server.py:608-704` sends SIGTERM (with optional SIGKILL escalation at L683-690 emitting `task.cancel_escalated`), then sets `TaskState.CANCELED` via `self._state.update(task_id, state=TaskState.CANCELED)` at `src/popolaloom/daemon/server.py:695` — but the supervisor wait thread will *still* see the subprocess exit (likely with a non-zero exit code from SIGTERM/SIGKILL) and emit `task.failed`, NOT `task.canceled`. Grep across `src/popolaloom/daemon/` for the literal `task.canceled` returns **no matches**. The evaluation runner at `src/popolaloom/evaluation/runner.py:325-331` reads `type_counts.get("task.canceled", 0)` and adds it to the terminal-event evidence — i.e. the runner *expects* a `task.canceled` event that the daemon never emits. This is a **latent contract bug** worth flagging in v0.4.1 because it silently distorts the nines composite (cancel-counted-as-failure inflates the failure rate).

Resolution options for v0.4.1:

1. Have `cancel_task` itself append `task.canceled` to the event log *before* sending SIGTERM (loses the actual exit_code), or
2. Have the supervisor's wait thread check the StateStore's terminal state at exit time and emit `task.canceled` (with exit_code) if `TaskState.CANCELED` is set (preserves exit_code, requires StateStore access).

Option 2 is cleaner and keeps the supervisor as the sole emitter of terminal events.

### §D.6 — Insertion points for proactive notification

The natural insertion point for v0.4.1 proactive notification is `Popolad._on_subprocess_exit` at `src/popolaloom/daemon/server.py:867-905` (the wait-thread callback that updates StateStore to COMPLETED / FAILED). This callback runs after every terminal event is appended to the event log, has the `task_id` + `exit_code`, and can synchronously look up the original prompt + cli adapter from the registered `TaskHandle`. A new helper `notify_lark_terminal(task_id, terminal_state, exit_code, popolad)` invoked here would hit `send_lark_card` (or a new `send_lark_completion_card` builder) with a completion / failure card built from a parallel taxonomy of `LARK_TERMINAL_TRIGGERS` — see §E.2 for the proposed shape.

The HITL-prompt-await path (`hitl/sync.py` → `LarkRenderer.send`) already exists; v0.4.1 should reuse the same `send_lark_card` retry / timeout / metadata-key plumbing rather than open-coding a new subprocess invocation.

#### §E.2.2 — Wiring point (exact module + function)

The minimal wire-up adds:

1. A new `popolaloom.lark.notifier` module (~ 100 LOC) exposing `send_terminal_notification(popolad, task_id, terminal_state, exit_code) -> NotificationOutcome`.
2. In `popolaloom.lark.card_templates`, four new builders: `build_completion_card`, `build_failure_card`, `build_canceled_card`, `build_cancel_escalated_card` (each calling `footer_with_origin_note`).

## §F — Discrepancies + risks for L1 Design

### §F.1 — `send_lark_card` no production call sites in `src/popolaloom/daemon/`

Confirmed by grep: `send_lark_card` appears in `src/popolaloom/hitl/sync.py:335` (outcome recorder, not invoker), `src/popolaloom/hitl/renderers/lark.py:113-205` (definition + retry + log lines), and zero references inside `src/popolaloom/daemon/`. The daemon process therefore never sends a Lark card today as a side effect of task lifecycle events. v0.4.1 must close this; design must decide between (a) reusing `send_lark_card` for terminal notifications (simpler, share retry / timeout / log lines) or (b) a new `send_terminal_card` (cleaner separation of HITL vs notification semantics). Recommendation: option (a) with an extra `kind: Literal["hitl","terminal","notification"]` arg threaded through for log-line distinguishability.

### §F.2 — `daemon/main.py` no LarkListener wiring

Confirmed by reading `src/popolaloom/daemon/main.py:142-173` — only `build_command`, `_build_persistence_safely`, `Popolad`, `PopolaEventBusBridge` are referenced. `LarkListener` and `LarkSupervisor` are not imported. Inbound Lark events thus have no daemon ingress; the existing test fixtures must be running these out-of-band. Closing this gap is in v0.4.1 §E.2.2 step 5.

### §F.3 — `cancel_task` does not emit `task.canceled`

Confirmed by:

- `src/popolaloom/daemon/supervisor.py:220` only emits `task.completed` / `task.failed`.
- `src/popolaloom/daemon/server.py:608-704` (`cancel_task`) emits `task.cancel_escalated` (only on SIGKILL escalation, L686-690) but NOT a `task.canceled` baseline.
- `grep -rn 'task.canceled'` across `src/popolaloom/daemon/` returns zero matches.
- `src/popolaloom/evaluation/runner.py:325-331` consumes `type_counts.get("task.canceled", 0)` — i.e. the runner expects an event the daemon never emits.

This is a **latent contract bug** that distorts the nines composite (cancellations are double-counted as failures because the supervisor wait-thread sees a non-zero exit_code from SIGTERM). v0.4.1 closes per §E.2.2 step 4 — Option 2 (StateStore-aware supervisor) preferred.

### §F.4 — `evolution/skill_inject.py` path constants are CORRECT (not a bug)

The prior survey flagged a "possible bug" because `skill_inject.py` uses `~/.cursor/skills/` while the survey claimed Cursor skills lived at `~/.cursor/skills-cursor/`. **This finding is incorrect.** Verified by:

1. `ls /root/.cursor/skills/devola-flow/` returns `SKILL.md`, `examples/`, `references/`, `.devola-flow-version` — confirming `~/.cursor/skills/devola-flow/SKILL.md` is a real install location.
2. The DevolaFlow installer at `init_project.py:194-202` writes to `base_dir / "skills" / "devola-flow"` (where `base_dir = Path.home() / ".cursor"` for `--global`).
3. The `~/.cursor/skills-cursor/` directory contains only Cursor IDE's bundled skill catalogue (`babysit`, `canvas`, `create-hook`, etc.) — it is the IDE's own asset directory, not an install target for third-party skills.

Therefore `skill_inject.py:41-45` is correct. No code change needed for this concern. The L1 design stage should NOT accept the "possible bug" as a real finding; it is resolved here in §F.4 with evidence.

### §F.5 — Other anomalies found while reading

- **`mcp/tools.py:42-56` lists `popola_supply_feedback` and `popola_inject_subtask` as deferred to v0.3.0** but the comments at `src/popolaloom/mcp/tools.py:14-18` say they were deferred originally to v0.3.0 F4 / F2. Per the v0.4.0 release notes the F4 HITL stack landed (1500+ LOC per `pyproject.toml:111-112` comment); the design stage should verify whether the deferred markers are now stale and update `__all__` / docstrings accordingly.
